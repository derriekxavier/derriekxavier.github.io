The brief I set myself

Most portfolio dashboards show a clean number and stop there. I wanted to build something that also showed the mess underneath it — because real retail data always has orphaned foreign keys, invalid prices, and missing currency codes, and a report that hides that isn't more useful, it's less trustworthy. So GulfCart has a page most tutorial projects skip entirely: Data Quality.

Executive Summary

The landing page answers the three questions a stakeholder actually opens a report to ask: what did we make, how healthy is the margin, and how did that break down by channel and category. A metric selector lets the same visual set flip between Net Revenue, Gross Revenue, Net Revenue after Returns, Gross Margin, Orders, Units, and Average Order Value without duplicating pages.

What's modelled here

  • Net Revenue, Gross Margin, Margin %, Return Rate (Value) as core measures, all channel- and year-filterable
  • A disconnected measure-selector table driving the KPI card and trend chart, so one visual serves seven metrics
  • Category-level table combining Net Revenue, Target, Attainment %, Margin %, and Return Rate side by side for quick scanning

Why it's built this way

A metric-selector pattern (bind a slicer to a disconnected table, then SWITCH on the selected value inside one measure) keeps the report from sprawling into a dozen near-identical charts. It's the same technique used in the BI Gauntlet build — I reused it deliberately once I'd proven it worked.

Category & Product

Drills from the summary numbers into where margin is actually being won or lost — by category, and by return behaviour, which quietly erodes margin in ways a top-line revenue number never shows.

Electronics and Fashion carry the largest revenue share, but Sports shows the widest negative target variance and the highest return rate — the kind of divergence that a single blended margin number would hide. Order lines that couldn't be matched to a product are kept under an Unknown category with their revenue intact, following the Kimball "unknown member" pattern rather than silently excluding them.

Customer

RFM segmentation and a full month-by-month cohort retention matrix, because "new vs returning revenue" on its own doesn't say whether the business is actually retaining anyone.

RFM segments are scored at 180 days recency, 5 orders frequency, and AED 30,000 monetary value — thresholds documented directly on the page rather than left implicit in a measure someone would have to reverse-engineer. The cohort table tracks retention percentage for every acquisition year and quarter against every subsequent month, which is what actually lets you see whether retention is improving year over year (2024 and 2025 cohorts consistently outperform 2022's, month for month).

Data Quality

This is the page I'm most glad I built. 2,497 rows were excluded from the model during cleaning — and every one of them carries a reason code rather than disappearing silently.

What was rejected, and why

  • 1,038 rows — orphaned order IDs referencing an order that didn't exist in the orders table
  • 836 rows — invalid quantities or unit prices
  • 407 orders — missing currency codes or unparseable dates
  • 177 returns — invalid return dates or returns dated before their originating order
  • 78 tier-history rows — invalid validity date ranges

Separately, 810 order lines couldn't be matched to a product and 563 lines across 258 orders couldn't be matched to a customer. These weren't excluded — they were retained under an unknown-member key so their revenue stays in the totals, which matters because dropping them would quietly understate revenue for a reason that has nothing to do with the business.

Power Query approach

Each source table gets validated on ingest; failing rows are routed to a rejects table with a reason code column rather than filtered out invisibly. That reason code is what drives the chart on this page — the query logic and the report visual share the same vocabulary, so the report is a direct read of what the transformation layer actually did.

What I'd extend next

  • Add a reconciliation KPI (rejected-row value as a % of total order value) so the data-quality page ties numerically back to the executive summary
  • Push RFM scoring thresholds into parameters so they can be tuned without editing DAX
  • Add a returns-reason breakdown to pair with the existing return-rate visuals
